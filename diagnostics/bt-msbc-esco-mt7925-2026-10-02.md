# mSBC eSCO link comes up empty and is never released (MT7925, kernel 7.0)

Date: 2026-10-02. Adapter: MediaTek MT7925 Bluetooth over USB (13d3:3602), btusb, kernel 7.0.0-34-generic
(Ubuntu 24.04 HWE), BlueZ 5.72, PipeWire 1.0.5, WirePlumber 0.4.17, native HFP backend. Headset: Poly Voyager
Legend 50 (HFP codecs CVSD + mSBC). Reproduced with BT firmware builds 20260813113236 and 20260605184935.
The kernel logs `HCI Enhanced Setup Synchronous Connection command is advertised, but not supported.` for this
adapter, so the legacy Setup Synchronous Connection command is used.

## Symptom

Call apps switch the headset to HFP, the microphone node appears, but no audio flows. WirePlumber logs
`Failure in Bluetooth audio transport`; with `WIREPLUMBER_DEBUG=5,spa.bluez5*` the transport logs
`acquire failed: Operation not supported (-95)`. Roughly one call after a headset reconnect works, all later ones fail.

## HCI trace (`sudo btmon`, text output)

mSBC attempt right after a fresh headset connection:

```
< HCI Command: Setup Synchronous Connection (0x01|0x0028) plen 17
> HCI Event: Command Status                     Status: Success (0x00)
> HCI Event: Synchronous Connect Complete (0x2c)
        Status: Success (0x00)   Link type: eSCO (0x02)   Air mode: Transparent (0x03)
        Transmission interval: 0x0c   Retransmission window: 0x04   RX/TX packet length: 60
```

In that capture no stream was attached to the headset nodes yet, so no `SCO Data` followed; with a stream attached
the mSBC link does carry audio. The defect is what comes next: no `Disconnect` command for the eSCO handle when
PipeWire releases the transport. The eSCO link stays up until the ACL link to the headset is
dropped (headset disconnect or adapter power-cycle), where the controller reports it closed together with the ACL.

Every later attempt while that link exists:

```
< HCI Command: Setup Synchronous Connection (0x01|0x0028) plen 17
> HCI Event: Command Status
        Status: Unsupported LMP Parameter Value / Unsupported LL Parameter Value (0x20)
```

A Command Status failure is final for the kernel (no retry over the other eSCO parameter sets), so the SCO socket
connect fails immediately with EOPNOTSUPP.

Same trace with mSBC disabled (HFP negotiates CVSD) or with HSP: `Synchronous Connect Complete` with CVSD air mode,
SCO data flows in both directions (about 1,300 packets per second of call), and the kernel sends `Disconnect` for the
eSCO handle when the stream ends. A few `SCO Data RX` packets arrive after the Disconnect; the kernel logs them as
`SCO packet for unknown connection handle`, which is harmless.

## Numbers (`configs/bluetooth/bt-headset-mic-test.sh`, 6 s Communication-role capture per attempt)

| mode | attempts | link up with audio |
|---|---|---|
| HFP + mSBC, re-established per call | 22 | 1 (the first after a reconnect) |
| HFP + mSBC, profile held manually | calls | works, wideband |
| HFP + CVSD (mSBC disabled) | 8 | 8 |
| HSP | 14 | 13 |

## What works

Switching the headset to "Headset Head Unit (HSP/HFP, codec mSBC)" manually in GNOME Sound settings and leaving
it there: the mSBC link is set up once, carries audio in both directions at wideband quality, and stays up across
calls. The defect only bites when the link must be re-established, i.e. after a switch back to A2DP or with
WirePlumber's automatic profile switching at call start. If a manual switch back to the headset profile ends in
silence, disconnect and reconnect the headset once to drop the stale link.

Alternatives measured: `bluez5.enable-msbc = false` makes HFP negotiate CVSD, which is re-established reliably
(8 of 8) but is narrowband; HSP behaves the same (13 of 14).

## Root cause and fix (2026-10-07)

PipeWire issue [#5506](https://gitlab.freedesktop.org/pipewire/pipewire/-/issues/5506), community fix
[abrus861/pipewire-hfp-atbcc-fix](https://github.com/abrus861/pipewire-hfp-atbcc-fix). The headset sends `AT+BCC`
(headset-initiated codec connection) about 160 ms after the AG has started the eSCO connect. The native backend answers
`+BCS:<current codec>`, the headset confirms `AT+BCS=<same>`, and the `AT+BCS=` handler frees and re-creates the
transport, closing the SCO socket while its connect is in progress. The kernel sends Create Connection Cancel, which does
not cancel an eSCO setup; the controller completes the link, the host has no connection for it, hence no Disconnect and
the 0x20 refusals. That is exactly the `RFCOMM << AT+BCC` / `transport free` sequence in the WirePlumber debug log above.

Fix: in the `AT+BCS=` handler, when a transport exists and the confirmed codec equals the one in use, reply OK and keep
the transport (no codec_switched event). Backported to PipeWire 1.0.5 in
`configs/bluetooth/pipewire-hfp-atbcc-fix/`, built and installed user-locally by
`configs/bluetooth/install-spa-bluez5-fix.sh`. Result on the same machine, stock WirePlumber policy, mSBC enabled:

| mode | attempts | link up with audio |
|---|---|---|
| HFP + mSBC, unpatched | 22 | 1 |
| HFP + mSBC, patched plugin | 8 | 8 |

Not a kernel or firmware problem; the eSCO data path and teardown work once the socket is not closed mid-connect.

## Open

Upstream merge of the fix (not in any release up to 1.6.9 as of October 2026). The kernel-side behaviour that an eSCO
setup cannot be cancelled by closing the socket is a separate, pre-existing limitation.
