# mSBC eSCO link comes up empty and is never released (MT7925, kernel 7.0)

Date: 2026-10-02. Adapter: MediaTek MT7925 Bluetooth over USB (13d3:3602), btusb, kernel 7.0.0-34-generic
(Ubuntu 24.04 HWE), BlueZ 5.72, PipeWire 1.0.5, WirePlumber 0.4.17, native HFP backend. Headset: Poly Voyager
Legend 50 (HFP codecs CVSD + mSBC). Reproduced with BT firmware builds 20260813113236 and 20260605184935.
The kernel logs `HCI Enhanced Setup Synchronous Connection command is advertised, but not supported.` for this
adapter, so the legacy Setup Synchronous Connection command is used.

## Symptom

Call apps switch the headset to HFP, the microphone node appears, but no audio flows. WirePlumber logs
`Failure in Bluetooth audio transport`; with `WIREPLUMBER_DEBUG=5,spa.bluez5*` the transport logs
`acquire failed: Operation not supported (-95)`. Roughly one call after a headset reconnect works, all later ones fail.

## HCI trace (`sudo btmon`, text output)

mSBC attempt right after a fresh headset connection:

```
< HCI Command: Setup Synchronous Connection (0x01|0x0028) plen 17
> HCI Event: Command Status                     Status: Success (0x00)
> HCI Event: Synchronous Connect Complete (0x2c)
        Status: Success (0x00)   Link type: eSCO (0x02)   Air mode: Transparent (0x03)
        Transmission interval: 0x0c   Retransmission window: 0x04   RX/TX packet length: 60
```

After that: zero `SCO Data` packets in either direction for the whole session, and no `Disconnect` command for the
eSCO handle when PipeWire releases the transport. The eSCO link stays up until the ACL link to the headset is
dropped (headset disconnect or adapter power-cycle), where the controller reports it closed together with the ACL.

Every later attempt while that link exists:

```
< HCI Command: Setup Synchronous Connection (0x01|0x0028) plen 17
> HCI Event: Command Status
        Status: Unsupported LMP Parameter Value / Unsupported LL Parameter Value (0x20)
```

A Command Status failure is final for the kernel (no retry over the other eSCO parameter sets), so the SCO socket
connect fails immediately with EOPNOTSUPP.

Same trace with mSBC disabled (HFP negotiates CVSD) or with HSP: `Synchronous Connect Complete` with CVSD air mode,
SCO data flows in both directions (about 1,300 packets per second of call), and the kernel sends `Disconnect` for the
eSCO handle when the stream ends. A few `SCO Data RX` packets arrive after the Disconnect; the kernel logs them as
`SCO packet for unknown connection handle`, which is harmless.

## Numbers (`configs/bluetooth/bt-headset-mic-test.sh`, 6 s Communication-role capture per attempt)

| mode | attempts | link up with audio |
|---|---|---|
| HFP + mSBC | 22 | 1 (the first after a reconnect) |
| HFP + CVSD (mSBC disabled) | 8 | 8 |
| HSP | 14 | 13 |

## Workaround

`bluez5.enable-msbc = false` in a WirePlumber bluetooth.lua.d drop-in (installed by
`configs/bluetooth/install-bt-headset-autoswitch.sh`). Calls are narrowband but reliable.

## Open

Whether the empty transparent link is the btusb isochronous alt-setting path for MediaTek (no kernel log either way)
or PipeWire's native backend not driving the socket, and why no Disconnect follows the release. Not yet tested on the
6.17 OEM kernel.
